# Dataset card — Rahgir synthetic algorithm benchmark

**Version:** 0.1.0  
**Prepared:** 17 November 2026  
**Dataset type:** generated synthetic optimisation fixtures  
**Intended use:** unit testing and controlled algorithm/indicator experiments only

## Summary

The current benchmark dataset is generated by `research/run_experiments.py`. It contains eight independently seeded synthetic itinerary-selection instances. Each instance contains twelve candidate POIs with artificial category, cultural-value, preference, metadata-completeness, detour-time and detour-distance features. Five NSGA-II random seeds are run on each fixed instance. The exact Pareto reference front is obtained by enumerating all 4096 binary subsets for each instance.

The checked-in `synthetic_benchmark.csv` contains 160 rows: 8 instances × 5 optimizer seeds × 4 algorithms. It records the fixture seed, algorithm, candidate count, exact reference-front size, returned front size, hypervolume estimate, IGD, runtime, feasibility rate and mean stop count.

## What it does not contain

It contains **no** live Indian road geometry, current travel times, actual POI records, authoritative cultural facts, operational opening hours, traffic conditions, verified safety incidents, community observations, human relevance labels, participant responses, or measured emissions. The five named Indian routes in the application are separate synthetic walkthrough fixtures and are not this benchmark's empirical route dataset.

## Collection and generation

No human subjects or personal data are involved. Problem instances are generated from fixed pseudo-random seeds by the synthetic generator in `run_experiments.py`. Optimizer seeds are changed while each generated instance stays fixed across algorithms. The independent statistical unit is the generated instance (eight units); the five optimizer seeds are repeated algorithm runs within each instance.

## Data fields

- `instance_id`, `seed`, `fixture_seed`: instance and run provenance.
- `algorithm`: NSGA-II or one of the three simple baselines.
- `candidate_count`, `reference_front_size`, `returned_front_size`: problem and output dimensions.
- `hypervolume_3d_mc`: fixed-reference Monte-Carlo hypervolume over the first three objective dimensions.
- `igd_6d`: inverted generational distance to the exact six-objective synthetic reference front.
- `runtime_ms`: measured elapsed time for the corresponding algorithm invocation in the execution container.
- `feasibility_rate`, `mean_stops`: generated-instance feasibility diagnostics.

## Limitations and bias

Synthetic feature distributions and objective interactions are assumptions made by the benchmark author. They may favour the objective formulation and search procedure under test. The nearest-feasible, distance-only and weighted-greedy baselines are intentionally simple and are not state-of-the-art TTDP solvers. Eight instances provide low external validity even when paired exact tests produce small p-values. The hypervolume metric is a three-objective projection, while IGD is six-dimensional; they capture different aspects of solution quality and should not be conflated.

The benchmark cannot support claims about actual route quality, cultural accuracy, hidden-gem authenticity, real-user satisfaction, safety, reduced crashes, or practical superiority in India.

## Licensing and redistribution

The generated fixtures and experiment code are original project artefacts. They contain no external map-provider extracts. The benchmark is intended to be shared with the project source; inspect the root project licence before assigning a broader reuse licence.

## Future data additions

Live route snapshots must be stored separately with provider identifiers, retrieval timestamps, request parameters, raw response hashes, attribution/licence notes, and retention policy. Human relevance judgements require a rubric, consent, annotator pseudonyms, disagreement analysis and route-level data splits. Safety data require an authoritative, licensed source with explicit geographic and temporal coverage. Do not merge those datasets into the synthetic partition without an explicit `data_partition` field.
